# NoshU
# 
**Multi-venue campus food ordering platform.** Students order ahead and track pickup live; venue staff manage incoming orders and menu availability from a real-time dashboard.

## What is NoshU?

NoshU lets students browse a venue's menu, place an order, and watch it through to pickup — all from their phone, with no account required. Each venue's staff get a live dashboard to receive orders, update their status, and mark items out of stock the instant they run out.

It's not a single restaurant's app — it's a small marketplace of independent campus venues (**ARK Cafe**, **Main Cafeteria**, **WOW Fries**) sharing one visual identity, one codebase, and one backend, while keeping each venue's orders, menu, and staff logins fully separate.

| | |
|---|---|
| **Venues** | ARK Cafe · Main Cafeteria · WOW Fries |
| **Frontend** | Static HTML / CSS / vanilla JavaScript |
| **Backend** | [Supabase](https://supabase.com) — Postgres + Realtime + Auth |
| **No student account needed** | Orders are tracked locally per-browser and synced live via Supabase |

## ✨ Features

### For students
- Browse a live, per-venue menu with category filters (Meals / Drinks / Snacks)
- Add items to a running cart with a floating cart bar and quantity steppers
- **Out-of-stock awareness** — unavailable items are greyed out with an "Unavailable" badge and disabled ordering, updated live the moment staff toggle them
- Checkout with name / phone / optional enrollment / payment method (Cash or Wallet)
- Live **MM:SS pickup countdown**, estimated from the slowest item category in the order
- Durable receipts — close the tab or the whole browser, the countdown picks up right where it left off
- An "active orders" banner/dropdown tracking every in-flight order across every venue

### For venue staff
- Real-time dashboard of every order for their venue, with status pills (`Preparing` → `Ready to pick up` → `Delivered`)
- One-click status updates and order removal (once picked up/delivered)
- Toggle "Out of stock" or leave a comment (e.g. *"Running low"*) on any menu item — instantly reflected on every student's screen
- Secure, venue-scoped login — an ARK Cafe account can never view WOW Fries' orders, even by guessing the URL

### Under the hood
- Realtime sync via Supabase `postgres_changes` subscriptions (≈1s propagation), with a 5s polling fallback
- Row-Level-Security-backed Postgres tables as the entire access-control layer
- Clean migration path from a local-storage-only prototype to a fully networked backend (see [`Architecture`](#-architecture) below)

```

┌─────────────────┐               ┌──────────────────┐
│ index.html       │               │ login.html        │
│ ark/main/wow.html│──┐         ┌──│ staff_*.html       │
│ checkout.html    │  │         │  └──────────────────┘
└─────────────────┘  │         │
                      ▼         ▼
              ┌───────────────────────┐
              │        Supabase        │
              │  Postgres + Realtime   │
              │  ┌─────────┐ ┌───────┐ │
              │  │ Orders  │ │ Item_ │ │
              │  │         │ │ state │ │
              │  └─────────┘ └───────┘ │
              │  ┌───────┐             │
              │  │ staff │  + Auth     │
              │  └───────┘             │
              └───────────────────────┘
```

**Two generations of this app exist:**

1. **v1 — local-only prototype.** Everything (orders, item availability, cart, staff session) lived in `localStorage`/`sessionStorage`. Worked great on one browser, broke the moment a student's phone and a staff laptop needed to see the same data.
2. **v2 — Supabase-backed (current).** Every shared-state key was replaced with a real Postgres table, synced live over websockets. Only the in-progress cart (`sessionStorage`) and "which order IDs belong to me" (`localStorage`) remain client-side, since neither needs to be shared.

## 🗄 Database schema

Three tables, all with Row Level Security enabled.

<details>
<summary><code>Orders</code></summary>

```sql
create table public."Orders" (
  id bigint generated by default as identity not null,
  created_at timestamp with time zone not null default now(),
  status text null default 'Preparing'::text,
  items jsonb not null default '[]'::jsonb,
  venue text not null default 'ark'::text,
  venue_name text null,
  display_code text null,
  total integer not null default 0,
  student_name text null,
  phone text null,
  enrollment text null,
  payment text null,
  estimated_minutes integer null,
  constraint Orders_pkey primary key (id)
);
```
</details>

<details>
<summary><code>Item_state</code></summary>

Per-venue, per-item availability — `(venue, item_id)` unique, plus `out_of_stock boolean` and `comment text`.
</details>

<details>
<summary><code>staff</code></summary>

```sql
create table public.staff (
  id bigint generated by default as identity primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  venue text not null
);
```
Maps a Supabase Auth user 1:1 to the single venue they manage.
</details>

> ⚠️ RLS policies in this project are intentionally permissive (`using (true)`) since only the public `anon` key is used — see the full documentation report for the reasoning and the exact policy SQL.

## 🚀 Getting started

1. **Create a Supabase project** at [supabase.com](https://supabase.com).
2. **Run the schema SQL** (see [`Database schema`](#-database-schema) / the full docs) in the SQL editor to create `Orders`, `Item_state`, and `staff`, and enable RLS + policies on each.
3. **Turn on Realtime replication** for `Orders` and `Item_state` under **Database → Replication**.
4. **Create staff accounts** under **Authentication → Users**, and seed matching rows into `staff` mapping each user to a venue.
5. **Add your Supabase credentials** (project URL + anon key) to the client config used by the HTML pages.
6. **Serve the site** — any static file server works, e.g.:
   ```bash
   npx serve .
   ```
7. Open `index.html` for the student flow, or `login.html` for the staff dashboards.
